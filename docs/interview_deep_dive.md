# 项目面试深讲：从"不懂"到"能讲"

> 配套文档：`docs/interview_guide.md`（30 秒复习稿）、`docs/hybrid_retrieval_tuning.md`（调优原始记录）、`docs/ai_agent_job_hunting_guide_for_beginner.md`（小白学习版）。
> 本文档解决三个问题：①把项目讲懂（大白话）；②难点与"我怎么解决的"；③RAG 调优 & Agent 编排设计动机，以及面试怎么讲。

---

## 第 0 步：一句话说清项目

**给客服主管用的 AI 助手**：业务人员用自然语言问"质量退款超 100 元的明细按 SOP 要不要主管复核"，系统自动决定"查数据 + 查政策 + 安全拦截"，返回可追溯的结论（带数据明细、SOP 引用、执行轨迹）。

它不是聊天机器人，是**把 LLM 放进受控工具链里的企业应用**——模型只负责"理解意图、选工具"，真正的数据查询、权限、安全、审计都由后端代码控制。

---

## 第 1 步：先懂业务，才能懂设计

客服主管每天面对三类问题，每一类都对应一个执行模式：

| 业务问题 | 例子 | 对应执行模式 |
|---|---|---|
| 要**数据** | "查询质量问题退款超过100元的明细" | `function_call_agent`（工具链查 SQL） |
| 要**规则** | "3C 拆封后质量问题怎么处理？" | `langchain_rag`（检索 SOP 回答） |
| **数据 + 规则**都要 | "这些高赔付明细按 SOP 要不要主管复核？" | `sql_rag_chain`（先查数据，再检索政策判断） |

这就是整个架构的出发点：**业务天然分三类，所以路由到三个模式，而不是一个万能 Agent**。
这样做的收益：每个模式内部简单可控、可解释、可单独评测。

---

## 第 2 步：一条请求的完整旅程（大白话）

以"质量退款超过100元的明细，按 SOP 是否需要主管复核"为例：

```
用户提问
  → ① JWT 鉴权（你是谁、什么角色）
  → ② Guardrail（有没有"退款/改单/删除/导出"等越权意图？有就拦截）
  → ③ AutoRouter 判定：这是"要数据+要规则" → sql_rag_chain
  → ④ 只读 SQL 工具查出"质量+超100元"的异常明细（模型不写 SQL，后端生成）
  → ⑤ 把明细摘要 + 原问题 交给 RAG，检索 SOP 判断复核规则
  → ⑥ SOP 没写死金额规则 → 不编造，给出建议 + 提示人工复核
  → ⑦ 返回：结论 + SQL预览 + 明细 + SOP引用 + 执行轨迹 + token/成本
  → ⑧ 写入审计日志，命中风险则进人工复核队列
```

面试金句：**这个链路体现了"数据 + 规则 + 安全 + 复核"的业务闭环。**

## 第 3 步：为什么这样编排 Agent？（面试高频）

### 3.1 为什么路由到三种模式，而不是一个万能 Agent？

- **可解释**：每个模式职责单一，出问题能定位（是查数据错还是政策错）。
- **可评测**：`route` 评测集就是验证"该走哪条路"是否正确，93.3% 准确率可量化。
- **可控**：万能 Agent 容易"自由发挥"，受控模式不会。

### 3.2 为什么路由要"规则优先 + LLM 确认"？

这是本项目最值得讲的工程权衡之一：

- **纯规则**：确定性、零延迟、零成本、可离线评测，但覆盖不了口语化/英文/隐含意图。
- **纯 LLM 路由**：灵活，但慢、贵、可能抽风（同问题两次结果不同）。
- **本项目方案**：规则先判（给 LLM 一个 hint）→ LLM 独立确认 → LLM 挂了/不合法就用规则兜底。
  - 规则负责"稳"，LLM 负责"活"；`temperature=0` 保证可复现。

### 3.3 为什么 Guardrail 要在一切执行之前？

安全边界**不能依赖模型自觉**，必须是确定性规则：`MUTATION_PATTERNS`（改单/退款/删除）、`PROMPT_INJECTION_PATTERNS`（规则绕过）、`DATA_EXFILTRATION_PATTERNS`（全量导出）——命中即拦截并进人工复核。
四层防线：工具层不暴露写接口 → SQL 层只读校验 → 权限层 RBAC → 策略层 Guardrail。

### 3.4 为什么要有"确定性 fallback"？

LLM 可能超时、报错、或者没触发工具调用。项目准备了 `_respond_without_llm`：**纯规则解析直接调工具**，保证低配环境/LLM 故障时系统仍可用，并在返回里标记 `degradation_path`（降级路径）。这是"AI 应用的可用性工程"意识，面试加分点。

### 3.5 为什么工具要"受控注册"而不是让模型随便调？

模型只产出 `tool_calls`（工具名+参数），执行权在后端：参数化查询、只读校验、RBAC 校验、审计。**从机制上杜绝 SQL 注入和越权**——这是"不用模型直接写 SQL"的原因，是面试必问点。

### 3.6 为什么会有 sql_rag_chain？

真实客诉问题往往"既要数据又要规则"（高赔付明细 + SOP 复核标准）。做法：先查数据（`query_refund_cases`）→ 把明细摘要拼进问题 → 再检索 SOP 判断依据。单独 SQL 或单独 RAG 都答不了这类问题。

### 3.7 会话记忆有什么用？

客服对话是连续的："查这个订单物流" → "那退款资格呢？"——系统把 `order_id` 存进会话记忆，第二轮能复用。评测集里 `memory` 用例专门验证这点（100% 通过）。

## 第 4 步：RAG 是怎么工作的 + 怎么调优（面试核心）

### 4.0 检索演进史（面试开场故事，先讲这个）

检索不是一步到位，是**三代演进**，每代解决上一代的问题，而且**保留上一代做兜底**：

| 代 | 方案 | 实现 | 评测命中率 | 问题 |
|---|---|---|---|---|
| v1 | **词法启发式** `lexical_search` | 人工标注 keywords + 类别匹配 + token 重叠率，只搜 40 条政策条目 | **91.1%**（最快，p50 0.56ms） | "开卷考"：只覆盖政策，搜不到 SOP/FAQ 长尾；无统计权重，泛化差 |
| v2 | **BM25** `rank_bm25` | 中文 bigram 分词 + IDF 统计加权，覆盖全部 393 chunk | 88.9% | 评测集数字略降（不再"开卷"），但真正覆盖全量文档 |
| v3 | **混合检索** `hybrid_bm25` | BM25 + 向量 + RRF + 政策加权（调优后） | **88.9%** | 补语义通道，覆盖口语化/英文改写（评测集还没考出它的价值） |

**为什么 v1 的 91.1% 比 v2 还高？** 因为 v1 是"专家规则"：policies.json 里每条政策人工标了 keywords，打分时命中关键词直接 +2，这等于**开卷考**——评测集的问题本来就是围绕这些政策设计的。但它致命短板是**只搜 40 条政策条目**，SOP/FAQ/cases 那 353 个 chunk 它根本看不见；也没有 BM25 的 IDF 统计权重，对真实多样化的文本泛化差。所以它从主链路退位，**保留为兜底**：
- `function_agent` 无 LLM 时的确定性 fallback（`search_policy_docs` 工具）；
- 三级降级链最底层：向量不可用 → BM25 不可用 → lexical（"绝不崩"）；
- `--force-lexical` 离线快速基线（0.56ms/条，秒级出报告，零 LLM 成本）。

面试讲这段的收获：**展示"演进不推翻"的工程习惯——每一代方案都保留价值，旧方案降级为兜底或基线，而不是推倒重来。**

### 4.1 这里的 RAG 是"双路召回 + 融合"

```
问题 → 向量检索（bge-m3 embedding，语义相似）
     → BM25 检索（中文 bigram 分词，关键词匹配）
     → RRF（Reciprocal Rank Fusion）融合两路排名
     → 政策锚点加权（POL- 判责条目优先）
     → 取 top-3 作为上下文 → LLM 基于引用生成回答
```

知识库：40 条政策（判责锚点）+ 38 篇 SOP/FAQ/案例（约 393 chunk）。
为什么双路：关键词型问题（"坏损怎么赔"）BM25 强；语义改写型问题（英文、口语化）向量强。双路互补。

### 4.2 调优故事：55.6% → 88.9%（面试 STAR 讲法）

**S（情境）**：检索升级为混合双路后，53 个评测用例上 citation 命中率只有 **55.6%**，反而比旧的 BM25 单路（88.9%）**更低**——混合检索成了负优化。

**T（任务）**：定位为什么混合反而更差，并把它调到不低于单路水平。

**A（行动）**：
1. 对比单路路径（`_bm25_sources`）和混合路径（`query`）两段代码，发现**三处不一致**：
   - 候选池大小不一致：单路 BM25 召回 9 个，混合只召回 6 个——正确答案常排在第 6~9 位，融合池里根本没有它；
   - 单路有"政策锚点加权"（POL 条目 ×1.5），混合没有——长 FAQ/SOP chunk 把判责政策挤出；
   - RRF 无权重融合：向量 top-1 得分 ≈ BM25 top-3 得分，语义相近但**错误**的 FAQ 结果能挤掉正确的政策结果。
2. 把融合参数**配置化**（候选数 / 政策权重 / 融合权重，环境变量可控，默认不改变行为）；
3. 写了检索层快速评测脚本（不调 LLM，单轮 90 秒），**7 组实验**逐步验证：
   - BM25 融合权重 2.0 → 71.1%（证明加权方向有效）
   - 候选 9 + 政策加权 1.5 + 权重 2.0 → **88.9%**（达到评测上限）
   - 候选 12 / 政策加权 2.0 → 无增益，确认 88.9% 是当前评测集上限

**R（结果）**：citation 命中率 **55.6% → 88.9%**（+33.3pp），RAG 综合成功率 62.3% → 90.6%，负例拒答率/护栏/记忆保持 100%。最优参数固化为默认值；沉淀了快速评测脚本，后续每次调参成本降到 90 秒。

**面试怎么讲最后一句总结**：*BM25 在这类关键词型评测上本来就是更强的一路，混合检索的任务不是"五五开"，而是"保住 BM25 的正确结果，再用向量做语义补充"——所以我扩大了 BM25 候选池、给政策条目加权、融合权重向 BM25 倾斜。*

### 4.3 被追问怎么答

- **"为什么向量会拖累？"**：向量返回的是"语义相近但不同条款"的 chunk（问退货政策，返回退货 FAQ），无权重 RRF 下它和正确结果的分数几乎一样，占了 top-3 名额。
- **"为什么不直接砍掉向量？"**：评测集以关键词型问题为主所以 BM25 占优；向量对口语化/英文改写有价值（比如英文工具意图测试）。保留双路、调权重是性价比最高的方案，也保留了未来语义检索的潜力。
- **"RRF 的 k 是什么？"**：k 控制排名分数的衰减速度，k 越小越强调各列表头部。我在调参中保持 k=60，主要调候选池和权重，是因为问题出在"候选缺失"和"权重失衡"，不是排名平滑度。
- **"为什么不直接分数归一化后加权求和？"**：RRF 只依赖排名不依赖原始分数，跨检索器（向量距离 vs BM25 分数）尺度不同时更鲁棒，也更容易解释。
- **"评测集怎么保证公平？"**：53 条 RAG 用例分正例（标注期望命中文档）和负例（no-answer，验证不编造）；39 条 Agent 用例覆盖 route/tool/guardrail/memory 四类能力。负例拒答率 100% 说明 LLM 在上下文不足时不会编造规则。

## 第 6 步：面试问答预演（针对调优/编排/评测）

**Q：你做过最难的优化是什么？**
A：混合检索调优。加了向量后反而比单路差（55.6% vs 88.9%），通过对比两段代码发现候选池、政策加权、融合权重三处不一致，参数化后用 7 组实验调到 88.9%，并沉淀了 90 秒的快速评测工具。这个故事同时体现了定位问题、实验方法和工程化沉淀。

**Q：为什么集成 WeKnora（腾讯开源）？对你的项目有什么优化？**
A：分两层回答。**架构层面**：我把检索层抽象成可插拔（`RETRIEVAL_BACKEND` 环境变量切换），WeKnora 作为外部检索底座，上层 Agent 编排、Guardrail、评测体系、LLM 生成全部零改动——这是"架构解耦"，让企业可以按阶段选检索方案（先自研、后换成熟平台、甚至换商业服务）。**能力层面**：WeKnora 自带文档解析（PDF/Word/图片，我的自研只支持 md）、Web 知识库管理 UI、平台级权限与 API Key、pgvector/ES 等可扩展存储——这些是我的自研检索没有的。**效果层面（诚实）**：我拿同一套 53+39 评测对比过，当前场景下自研（调优后 88.9%）反而优于 WeKnora（文件名级 55.6%，且 id 体系不兼容）——所以我不会说"用了开源效果更好"，而是说"用评测驱动后端选型"：哪个适合哪个上。面试加分点在于：**我不是无脑引入开源，而是做了可插拔架构 + 量化对比**。

**Q：自研检索和 WeKnora 的区别是什么？**
A：自研是"轻量可控"：BM25 中文 bigram + bge-m3 + RRF 融合 + 政策锚点加权，跑在本机 Chroma，格式只支持 md/policies.json，好处是逻辑全在自己手里、能针对业务做政策加权、评测口径直接对齐。WeKnora 是"平台完整"：解析多格式、混合检索 + rerank、多种向量库、Web UI 管理、RBAC/API Key，好处是开箱即用、能扛更大规模，代价是部署重（Docker 全家桶）、返回的 chunk id 与本地 doc_id 体系不兼容（需要映射层）。选型的本质是"轻量可控" vs "平台能力"的权衡。

**Q：做两套检索不奇怪吗？正常项目不会这样做吧？**
A：分三点回答。**第一，演进使然**：项目不是一开始规划两套，而是"先自研跑通 → 再验证外部方案"的演进路径——任何真实项目都是演进出来的，不是设计出来的。**第二，定位不同**：自研是业务定制主链路（政策加权、评测对齐、轻量部署），WeKnora 是平台能力储备（多格式解析、Web 管理、可扩展存储），企业里"自研核心 + 集成平台"是很常见的组合。**第三，可插拔抽象的价值恰恰就是"对比与选型"**：正因为有两套，我才能用同一套评测客观对比、得出"当前场景自研更优"的结论——这不是重复劳动，而是"不预设谁好、用数据说话"的工程方法。类比：真实企业做技术升级时常见"双轨制"——生产跑 A 方案，同时验证候选 B 方案，等 B 达标再迁移。

**Q：WeKnora 效果更差，为什么没调优它？**
A：诚实说，有两层原因。**第一，"55.6%"不可直接比**：那是文件名级近似命中，因为 WeKnora 返回的是它自己的 UUID chunk id，和本地 POL-XXX 评测标注的 doc_id 体系不兼容——评测口径没对齐，这个数字本身就不能跟 88.9% 直接比较。要公平对比，得先加一层 doc_id 映射，或者按 WeKnora 的体系重新标注评测集。**第二，调优 ROI 的判断**：把 WeKnora 调好需要做映射层 + 调它的混合检索参数/rerank/embedding 选型，这是"在外部平台上做二次开发"，成本高；而自研这边 90 秒一轮、全可控，已经到 88.9%。当前阶段自研是主链路，WeKnora 是"能力储备 + 架构验证"，我的工程判断是**把精力放在 ROI 最高的地方**。所以我的表述是：WeKnora 集成做到了"链路打通 + 架构验证"，没做到"效果对齐"，真正要对齐，第一步加 doc_id 映射、第二步统一评测集调参——这是明确的下一步，不是已完成的成果。**面试里承认"做到哪一步"比吹"全都做了"可信得多**。

**Q：为什么不用 LangChain/LlamaIndex 的现成检索？**
A：项目用了 LangChain 的嵌入和生成，但融合逻辑（政策加权 + RRF 调参）是自己实现的——因为要针对业务（政策是判责锚点）做可控优化，也要能离线评测。

**Q：Agent 的"工具调用"和"插件"是什么关系？**
A：本质相同——LLM 输出工具名+参数，后端执行。项目做了受控注册：schema、权限、只读标记统一管理，并暴露了 MCP 接口，说明后续能对接 Agent 平台。

**Q：这个项目距离生产还差什么？**
A：真实只读账号、SSO、脱敏、监控告警、压测、线上审批系统。但评测、安全、审计、成本这些"落地才有的部分"我都做了——重点不是炫技，是把 AI 放进可控业务流程。

## 第 7 步：诚实边界（防被问倒）

## 附：1 分钟电梯陈述（背这个）

> 我做的项目是一个企业客诉 Copilot：客服主管用自然语言就能查异常退款、查订单物流、问售后 SOP，系统会自动判断"该查数据、该查政策、还是两者都要"，并给出带引用和依据的回答。核心设计有三个：一是分层路由，规则优先保证稳定、LLM 兜底保证灵活；二是把模型放进受控工具链，数据查询、权限、安全、审计都由后端控制，模型只负责选工具；三是检索与评测驱动，我把混合检索从 55.6% 调到 88.9%，中间定位到候选池、政策加权、融合权重三个问题并做了 7 组实验。同时补了 Guardrail、人工复核、token/成本追踪和自动化评测这些真实落地才需要的部分。
