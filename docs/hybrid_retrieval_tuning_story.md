# 混合检索调优：一个完整的故事（可背诵版）

> 说明：本文所有**数字与技术细节均为真实实验记录**（见 `docs/hybrid_retrieval_tuning.md` 与 `eval/results/tuning_report.json`）。
> 下面的"排查思路""当时的反应"等叙事细节，是为了让故事讲起来更完整。面试时请用第一人称真诚讲述，数字不能改。

---

## 引子：评测体系是怎么来的

在动手之前，我先给自己搭了一个"体检报告"——`eval/` 目录下 53 条 RAG 问答 + 39 条 Agent 能力用例，跑一次 `scripts/evaluate_rag.py` 就出一份报告，包含 citation 命中率、负例拒答率、路由准确率、工具选择准确率、护栏拦截率、多轮记忆准确率、时延、重试率。

为什么要先做这个？因为我清楚地知道：**没有量化指标，AI 应用就永远在"感觉差不多能用"的状态，没法证明任何改动是变好还是变坏。** 评测集就是我的尺子。

当时手上的基线数字是：
- BM25 单路：citation **88.9%**（40/45 正例命中）
- 词法启发式兜底：**91.1%**
- 负例拒答率：100%（8 个"没有答案"的问题，全部正确拒绝，不编造）

## 第一幕：混合检索上线

我决定把检索从"单路 BM25"升级成"向量 + BM25 双路 + RRF 融合"——这是当时的主流做法（hybrid retrieval）：

```
问题
 ├─ 向量检索（bge-m3，语义相似）  → 前 6 个候选
 ├─ BM25 检索（中文 bigram 分词） → 前 6 个候选
 └─ RRF（Reciprocal Rank Fusion）合并两路排名 → 取 top-3 → 交给 LLM
```

理论依据很充分：关键词型问题 BM25 强，口语化/同义改写型问题向量强，双路互补。向量库也建好了（393 个 chunk：40 条政策 + 38 篇 SOP/FAQ/案例）。

上线后我满怀期待地跑评测……然后被现实打脸。

## 第二幕：数字打脸

完整评测结果出来：

| 指标 | BM25 单路 | 混合双路（新） |
|---|---|---|
| citation 命中率 | 88.9% | **55.6%** |
| RAG 综合成功率 | 90.6% | **62.3%** |

**混合检索比单路还低了 33 个百分点。** 我花了几个小时把向量检索加进去，结果是最差的方案。第一反应是"是不是向量库坏了？"——查了 chunk 数（393）、embedding 模型（bge-m3）、向量库 manifest，全正常。

那问题只能出在"融合"这件事上。

## 第三幕：逐行对比代码，找到三处不一致

我做了最笨但也最有效的事：**把单路路径和混合路径两段代码并排逐行对比**。单路走 `_bm25_sources()`，混合走 `query()`。比着比着，发现三处关键差异：

**① 候选池大小不一致（我第一个发现的坑）**

单路路径：BM25 召回 `max(top_k * 3, 9)` = 9 个候选；
混合路径：BM25 只召回 `max(top_k * 2, 6)` = 6 个候选。

为什么这会致命？因为评测集里正确答案大多是政策条目（`POL-XXX`），而 BM25 检索一个中文问题，会返回很多"长文档 chunk"（SOP/FAQ 的分块），政策条目经常排在第 6~9 位。混合路径只取 6 个，**融合池里根本没有正确答案**——不是排错，是压根没进来。

**② 单路有"政策锚点加权"，混合没有**

单路路径里有一行很关键的领域知识：

```python
weight = 1.5 if str(doc_id).startswith("POL-") else 1.0
```

也就是说：政策条目（判责锚点）在 BM25 排序后还要再 ×1.5 加权，避免被更长的 FAQ/SOP chunk 挤出。这是之前沉淀的业务洞察——**售后判责必须先看政策**。但混合路径的 BM25 侧，这个加权**没有**。

**③ RRF 无权重融合，向量噪声有"席位优势"**

RRF 的分数公式是 `score = Σ 1/(k + rank)`，k=60。算一下：
- 向量 top-1：1/(60+1) ≈ 0.0164
- BM25 top-3：1/(60+3) ≈ 0.0159

**两者几乎一样大。** 而向量检索返回的往往是"语义相近但不同条款"的 chunk——比如用户问"7 天无理由退货政策"，向量返回的是退货 FAQ（因为语义都围绕"退货"）。这些错误结果 3 个加在一起，把 BM25 正确命中的政策条目硬生生挤出 top-3。

三个问题，一个比一个隐蔽，而且**任何单独一个都不会造成这么大差距，三个叠在一起才崩**。

## 第四幕：7 组实验，逐步逼近

我不打算"拍脑袋调"，而是把三个变量都**配置化**（环境变量控制，默认值不改变现有行为），然后一个一个变量验证。为此还写了 `scripts/eval_retrieval_probe.py`——一个只测检索层、不调 LLM 的快速脚本，把单轮评测从 3 分钟压到 90 秒，让"每试一组参数"的成本变得极低。

| # | 改了什么 | 命中率 | 我当时的解读 |
|---|---|---|---|
| 基线 | 默认参数 | 55.6% | 复现问题，确认基线 |
| 1 | BM25 融合权重 2.0 | **71.1%** | 方向对了！+15.5pp，证明"BM25 加权"有效 |
| 2 | 权重 3.0 | 71.1% | 咦，没变化？ |
| 3 | 权重 4.0 | 71.1% | 还是没变——说明权重 2.0 时 BM25 的正确结果**已经全部进 top-3 了**，再加重也没用，卡点不在这 |
| 4 | 候选 9 + 政策加权 1.5（权重回到 1.0） | 77.8% | 候选池和政策加权也各贡献了一部分 |
| 5 | **候选 9 + 政策 1.5 + 权重 2.0** | **88.9%** | 三项合起来追平了 BM25 单路！ |
| 6 | 候选 12 + 政策 1.5 + 权重 2.0 | 88.9% | 候选 9 已经够，扩大无用 |
| 7 | 候选 9 + 政策 2.0 + 权重 2.0 | 88.9% | 政策加权 1.5 已经够 |

实验 2/3 的"无变化"是个重要信号：它告诉我 71.1% 的瓶颈**不在融合权重**，而是还有别的因素在拖后腿——于是我才去动候选池和政策加权。**实验的价值不只是拿到好数字，更是排除错误假设。**

## 第五幕：为什么 88.9% 是上限（重要，面试会被问）

我试了候选 12、政策加权 2.0，都停在 88.9%。这时我意识到：**88.9% 恰好等于 BM25 单路的水平，说明混合检索已经"完全不输单路"了，而剩下的 5 个未命中不是参数问题**。

我把它们一个个拉出来看：

1. 「普通退货还在 7 天无理由范围内」→ 命中 POL-020 而非 POL-001：**关键词歧义**——两个政策都含"退货"，BM25 选了分数更高的那个；
2. 「食品里发现异物」POL-018：检索命中了 case 库但没进政策条目；
3. 「退款提交后一般多久到账」POL-019：**标注口径问题**——问题的答案其实更贴近 FAQ，但评测标注指向政策条目；
4. 「客服能说『你爱投诉就投诉』吗」POL-032：需要更深层的语义/情境理解；
5. 「大促超卖取消订单补偿」POL-001+POL-047：复合政策，单个条目的关键词匹配不够。

这 5 个问题，靠调融合参数解决不了——要么是标注口径（改评测集），要么需要 rerank 模型或问题分类路由（换机制）。**我如实把它们记录在调优文档里，作为下一阶段的迭代方向。** 面试里主动讲"我试到上限了，并且知道上限为什么是上限"，比吹"我调到了 100%"可信得多。

## 第六幕：收尾与沉淀

- **参数固化**：最优组合写进 `app/config.py` 默认值（BM25 候选 9 / 政策加权 1.5 / 融合权重 2.0），环境变量仍可覆盖，随时可回退实验；
- **工具沉淀**：`scripts/eval_retrieval_probe.py` 让检索层单轮评测从 3 分钟降到 90 秒，后续每次调参成本极低；
- **端到端验证**：重新跑完整评测（含 LLM 生成，DeepSeek V4 Flash）：

| 指标 | 调优前 | 调优后 |
|---|---|---|
| citation 命中率 | 55.6% | **88.9%** |
| RAG 综合成功率 | 62.3% | **90.6%** |
| 负例拒答率 | 100% | 100%（保持） |
| 路由 / 工具 / 护栏 / 记忆 | 93.3% / 90% / 100% / 100% | 全部保持 |

## 一句话总结（背下来）

> **我发现把向量加进来之后检索反而变差了（55.6% vs 88.9%），没有急着调参数，而是对比单路和混合两段代码，定位到候选池大小、政策锚点加权、RRF 融合权重三处不一致。我把参数配置化，用 90 秒一轮的快速评测做了 7 组实验，最终三项组合达到 88.9%，追平单路。这让我明白了一件事：混合检索的任务不是让两路五五开，而是保住更强一路的正确结果，再用另一路做补充——这也是我把最优参数固化成默认值、并把剩余 5 个边界 case 记录下来作为下一步迭代方向的原因。**

## 附：追问 10 连击（怎么答）

**Q0（最高频的质疑）：单路已经 88.9% 了，你为什么还要引入向量、把自己搞到 55.6%？这不是自己挖坑吗？**

这个问题一定要提前想清楚，答好了就是全场最亮的点。我的回答分四层：

**第一层：88.9% 是"测试分布内"的分数，不是"真实世界"的分数。**
我自建的评测集以关键词型问题为主（"坏损怎么赔""7 天无理由"），这类问题 BM25 天然占优。但真实客服问题远不止这些——口语化表达（"退钱"vs"退款"）、英文提问、同义改写（"衣服吊牌剪了"vs"影响二次销售的商品"）、无公共关键词的语义相关……这些都是 BM25 的结构性盲区。**单路的 88.9% 是在这个测试分布上成立，不代表在更广的真实分布上成立。**

**第二层：引入向量是"扩展能力"，不是"刷指标"。**
我加向量，是为了给检索系统多一条语义感知通道，让它能覆盖单路答不了的问题类型——这是能力建设，不是指标优化。上线初期掉到 55.6%，不是"方向错了"，是"融合实现没调通"（候选池、政策加权、RRF 权重三处问题）。

**第三层：回退→修复，恰恰是评测体系价值的证明。**
- 没有评测：上线混合检索 → "感觉差不多" → 55.6% 悄悄上线，埋雷。
- 有评测：上线混合检索 → 55.6% 立刻暴露 → 定位三处不一致 → 修复回 88.9%。
**评测的价值不是保证你不犯错，而是让你犯错的第一时间就知道，并且能量化、能归因、能修复。**

**第四层（诚实 + 前瞻）：我实测过，当前评测集下两路命中的 case 集合完全一致（40 个都中、5 个都未中），向量的独立贡献为 0。**
这恰好暴露了我评测集本身的局限——它没充分覆盖语义改写类问题，所以度量不出向量的价值。所以我的下一步迭代方向是：**扩充评测集，加入口语化、英文、同义改写用例，让向量的价值被真正度量出来。** 这句话面试官听了会点头：你既不自欺欺人，又知道评测的边界在哪。

一句话总结：**同等分数下，多一条语义通道的系统 > 单路系统——就像考同样的分，一个只会背这套卷子，一个真的懂了。当前测试集没考出差别，是我测试集的问题，不是能力的问题。**

## 附：追问 10 连击（怎么答）

**Q1：为什么向量检索会拖累？**
向量返回的是"语义相近但不同条款"的结果（问退货政策返回退货 FAQ），无权重 RRF 下它和正确结果分数几乎一样（1/61 vs 1/63），3 个错误结果能把 1 个正确结果挤出 top-3。

**Q2：为什么不干脆砍掉向量？**
评测集以关键词型问题为主，所以 BM25 占优；但向量对口语化/英文改写有价值（我的工具意图测试里有英文用例）。保留双路、调权重是性价比最高的方案，也保住了语义检索的扩展性。

**Q3：权重 3.0/4.0 为什么没变化？**
因为权重 2.0 时 BM25 的正确结果已经全部进入 top-3，继续加权重不会改变 top-3 的成员，只是数字变大。这反过来帮我确认了瓶颈不在权重，而在候选池和加权。

**Q4：RRF 的 k 是什么意思？**
k 控制排名得分的衰减速度，k 越小越强调各列表头部。我保持 k=60 没动，因为问题出在"候选缺失"和"权重失衡"，不是排名平滑度。

**Q5：为什么不分数归一化后加权求和？**
RRF 只依赖排名、不依赖原始分数，跨检索器（向量距离 vs BM25 分数）尺度不同时更鲁棒，也更好解释。

**Q6：评测集怎么设计的？公平吗？**
53 条 RAG 用例 = 45 条正例（标注期望命中的文档）+ 8 条负例（无答案，验证不编造）；39 条 Agent 用例覆盖 route/tool/guardrail/memory 四类。负例拒答率 100% 证明 LLM 上下文不足时不会编造规则。

**Q7：88.9% 是最高了吗？**
在当前评测集和当前机制下是。剩余 5 个 case 我分析过：关键词歧义、标注口径、语义抽象——需要 rerank 或问题分类路由才能解决，我如实记录为下一步方向。

**Q8：这个调优是离线做的吗？生产怎么保证？**
检索层调优用 90 秒的快速脚本（不调 LLM）做离线验证，最终参数用完整评测（含 LLM）确认。参数固化在配置里，环境变量可覆盖，任何改动都有评测报告兜底。

**Q9：向量库 393 个 chunk，规模这么小有意义吗？**
规模小但结构完整：政策 + SOP + FAQ + 案例四种类型。调优方法论（候选池/加权/融合）在更大规模上同样适用；而且小规模让我能快速迭代、逐 case 分析，这是我选择先在小数据上调通机制的原因。

**Q10：如果数据量到百万级 chunk 怎么办？**
分片 + 更好的向量索引（HNSW 参数）+ 检索后端可替换（我的 `RETRIEVAL_BACKEND` 抽象已经支持切换到 WeKnora 这类外部引擎），评测体系不变——这正是我设计"可插拔检索"的原因。
