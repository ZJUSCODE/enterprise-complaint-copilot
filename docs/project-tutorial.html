1 项目概述

1.1 这个项目是什么？

这是一个企业级 AI Agent 工作台原型，全称「企业级智能客诉预警与数据洞察 Copilot」。它的核心思路是：把大语言模型（LLM）的自由文本生成能力，约束在一个受治理、可审计、可解释的业务流程中。

一句话总结 这不是一个简单的聊天机器人。它是一个将 AI Agent 技术应用到真实企业场景（客诉处理、风险预警、政策检索）的完整工程实践。

想象一个场景：一个电商平台的客服主管，每天面对成千上万的用户投诉。哪些投诉需要立即升级？哪些订单的退款政策是什么？某个用户是不是高风险用户？传统做法是人工查数据库、翻政策文档、凭经验判断。这个项目做的事情是：你只需要用自然语言说出目标，系统自动判断意图、查询数据、检索政策、综合答案，并给出可追溯的证据链。

2 核心概念速成（零基础友好）

如果你刚接触 AI 应用开发，下面这些概念是你理解这个项目的「钥匙」。每个概念我都会用最通俗的语言解释。

2.1 大语言模型（LLM）是什么？

LLM 就是「大语言模型」——一个被训练来预测文本的超级神经网络。你可以把它理解为一个读过互联网上几乎所有文字、能根据你的问题续写答案的超级大脑。

但是 LLM 有两个致命问题：① 知识截止日期（训练数据有终点，比如它不知道昨天发生了什么）；② 幻觉（它有时会编造看起来很真但实际上不存在的信息）。这就是为什么我们需要 RAG。

2.2 RAG（检索增强生成）是什么？

核心思想 RAG = Retrieval-Augmented Generation。在让 LLM 回答问题之前，先去一个知识库里检索相关资料，把资料和问题一起塞给 LLM，让它「照着资料回答」。

类比：你去面试，面试官问你「你们公司的退款政策是什么」。你有两个选择：① 凭记忆回答（可能记错、记漏）；② 翻出政策文档，照着文档念（准确、有依据）。RAG 就是方案②的自动化版本。

RAG 的基本流程：文档 → 切碎成小块 → 用 Embedding 模型转成向量 → 存入向量数据库 → 用户提问时把问题也转成向量 → 在数据库中找最相似的块 → 把块+问题一起给 LLM → LLM 生成答案。

2.3 Agent / Function Calling 是什么？

Agent 是「能使用工具的 LLM」。普通 LLM 只能生成文字，Agent 能调用外部函数来获取真实数据。

在这个项目中，Agent 可以调用 7 个工具：查询订单、查物流、查退款资格、查用户风险、搜政策文档……这就像给 LLM 配了一组「手」，让它不只是说，还能做。

Function Calling 是 OpenAI 提供的一种机制：你告诉 LLM「我有哪些工具可用」，LLM 在需要时返回「我要调用工具 X，参数是 Y」，你的代码执行工具并返回结果，LLM 再根据结果生成最终答案。这就是所谓的 ReAct 循环（Reasoning + Acting）。

2.4 LangChain / LangGraph 是什么？

🔗 LangChain

一个 Python 框架，封装了 LLM 调用、向量数据库操作、提示词模板、链式调用等常见操作。它让 RAG 的开发更简单——不需要手写 ChromaDB 的 API，不需要手动管理 Embedding。

🕸️ LangGraph

LangChain 的「状态图」扩展。当你需要多个 Agent 按照一定逻辑协作时（比如先查数据、再查政策、最后综合），LangGraph 让你用「节点+边」的方式定义工作流，支持条件分支和循环。

2.5 MCP（Model Context Protocol）是什么？

MCP 是 Anthropic 提出的一个开放协议，目标是标准化 AI 模型与外部工具/数据源的交互方式。这个项目实现了 MCP 兼容的工具注册表——同一个工具可以被 Web UI 调用、被 API 调用、被 MCP 客户端调用，统一管理权限和安全。

2.6 SSE（Server-Sent Events）是什么？

SSE 是一种服务器向客户端推送数据的技术。普通 HTTP 请求是「一问一答」，SSE 是「一问多答」——服务器可以持续向客户端发送多个事件。

在 AI 应用中，LLM 生成答案需要几秒到几十秒。如果等全部生成完再返回，用户体验很差。用 SSE 就可以逐字输出—每生成一个 token 就推送给前端，像 ChatGPT 那样逐字显示。

2.7 JWT / RBAC 是什么？

🔑 JWT（JSON Web Token）

一种无状态的认证令牌。用户登录后服务器发一个签名的 token，后续请求带上这个 token 就能证明身份。服务器不需要存 session，靠签名就能验证真伪。

👥 RBAC（Role-Based Access Control）

基于角色的权限控制。这个项目有 3 个角色：viewer（只能查政策）、analyst（能查数据+审计）、supervisor（能人工复核）。不同角色能看到不同的页面、调用不同的工具。

2.8 向量数据库（ChromaDB）是什么？

向量数据库 是一种专门存储和检索「向量」（一串数字）的数据库。当文档被 Embedding 模型转换成一个 1536 维的向量后，这些向量被存入 ChromaDB。用户提问时，问题也被转成向量，ChromaDB 通过余弦相似度找到最接近的文档向量——这就是「语义搜索」的原理。

3.3 技术选型理由

为什么是 FastAPI？

异步支持好，自带 SSE（流式输出），Pydantic 集成用于数据校验，自动生成 OpenAPI 文档。比 Flask 更适合 AI 应用的高并发和流式场景。

为什么是 Vue 3？

响应式系统天然适合实时数据展示，Composition API 组织复杂逻辑清晰，Element Plus 提供企业级 UI 组件（表格、表单、对话框）。

为什么是 ChromaDB？

轻量级、嵌入式（不需要独立服务器），适合原型和演示。本地持久化，重启不丢数据。对于生产环境可以切换到 Milvus 或 Pinecone。

为什么是 LangGraph？

多 Agent 协作需要状态管理+条件路由，LangGraph 的状态图模型天然适合。同时支持回退到无 LangGraph 的函数式编排。

4 启动与初始化

4.1 启动链路：从 main.py 到全服务就绪

程序启动时，经历一条精心设计的依赖注入链。理解这条链路，就理解了整个系统的骨架。

核心概念：依赖注入 (Dependency Injection) 每个服务需要的其他服务，不是自己创建，而是从外部「注入」进来。好处是：① 解耦（各模块互相不依赖具体实现）；② 可测试（测试时注入 mock 对象）；③ 清晰（从初始化顺序就能看出系统结构）。

4.3 runtime.py 的巧妙设计

runtime.py 使用了一个 Python 黑魔法——__getattr__ 模块级访问器：

app/runtime.py — 延迟导入机制python
# 模块级 __getattr__：当有人写 from app.runtime import orchestrator 时，
# Python 发现模块没有 orchestrator 属性，就会调用这个函数
def __getattr__(name: str):
    if name == "settings":
        return get_runtime().settings
    if name == "orchestrator":
        return get_runtime().orchestrator
    if name == "tool_registry":
        return get_runtime().tool_registry
    # ... 更多服务
    raise AttributeError(f"module has no attribute {name!r}")

这样设计的好处：所有服务在第一次被访问时才创建（惰性初始化），避免了循环导入，也让测试代码可以方便地替换任何服务。

5 一次请求的完整生命周期

这是本文档最核心的章节。我们将追踪用户输入「查一下上个月高赔付的订单，有没有需要升级的？」从浏览器到后端再返回的完整旅程。

为什么这一章最重要？ 面试中，面试官最常问的问题就是：「用户发了一个请求，系统怎么处理的？」如果你能从头到尾清晰地讲清楚，就证明你真正理解了这个系统的设计。

5.1 请求生命周期全景（7 步）

①

前端发送请求

用户在 CopilotView.vue 输入框输入目标，按 Enter 发送。chat.ts store 的 sendMessage() 方法构建请求体，调用 streamChat()（SSE 流式传输）。如果流失败，自动回退到普通 POST。

前端 client.ts chat.ts

②

JWT 认证 → RBAC 权限校验

FastAPI 从 Authorization 头提取 Bearer Token → jwt_decode() 验证签名和过期时间 → 查询用户角色 → PermissionPolicy.can_use_mode() 检查该角色是否能使用请求的模式。

http_auth.py security.py permissions.py

③

安全护栏扫描

FunctionCallingAgent._guardrail() 扫描用户消息中的 4 类危险模式：写操作意图（「退款」「删除」）、提示注入（「忽略之前的指令」）、数据泄露（「显示所有用户密码」）、社会工程（「我是管理员」）。命中则阻断并推送到人工复核。

function_agent.py domain.py

④

智能路由决策

AutoRouter.route() 两级决策：① 规则路由：用正则和关键词匹配，置信度 ≥ 0.8 直接采用；② LLM 路由：规则不够自信时，让 LLM 在 5 种模式中分类；③ 默认回退：都失败则用 multi_agent。

当前消息包含「高赔付」「订单」→ 规则匹配为 function_call_agent，置信度高，直接采用。

routing.py

⑤

Agent 执行（核心）

路由到 function_call_agent 模式，进入 ReAct 循环：

第 1 轮：LLM 分析用户意图 → 决定调用 query_refund_cases 工具 → 参数 {category: null, complaint_type: null, amount_threshold: "high"} → _execute_tool() 分派到 ReadOnlySQLiteStore.query_ticket_details() → SQL 查询 Olist 数据库 → 返回 15 条高赔付记录。

第 2 轮：LLM 收到查询结果 → 判断需要进一步分析风险 → 调用 get_user_risk 工具 → 返回风险评分 → LLM 综合生成最终答案：「上个月有 15 笔高赔付订单，其中 3 笔用户风险评分 > 0.62，建议升级处理。详见下表：……」

function_agent.py ticket_store.py analytics.py

⑥

结果增强与质量评估

6.4 SSE 流式客户端：streamChat()

这是前端最复杂的函数，实现了完整的 SSE 流式接收：

frontend/src/api/client.ts — streamChat 核心逻辑typescript
export async function streamChat(
  request: ChatRequest,
  handlers: {
    onStatus?: (payload: StreamStatusPayload) => void;
    onToken?: (payload: { content: string }) => void;
    onFinal?: (payload: ChatResponse) => void;
  }
): Promise<ChatResponse> {
  const response = await fetch(apiUrl('/api/chat/stream'), {
    method: 'POST',
    headers: authHeaders({ 'Content-Type': 'application/json' }),
    body: JSON.stringify(request),
  });

  const reader = response.body!.getReader();
  const decoder = new TextDecoder('utf-8');
  let buffer = '';
  let finalPayload: ChatResponse | null = null;

  while (true) {
    const { done, value } = await reader.read();
    if (done) break;
    buffer += decoder.decode(value, { stream: true });

    // 按双换行拆分 SSE 事件
    const blocks = buffer.split(/\r?\n\r?\n/);
    buffer = blocks.pop()!;

    for (const block of blocks) {
      const eventMatch = block.match(/^event: (\w+)/m);
      const dataMatch = block.match(/^data: (.+)/m);
      if (!eventMatch || !dataMatch) continue;

      const event = eventMatch[1];
      const data = JSON.parse(dataMatch[1]);

      if (event === 'token') handlers.onToken?.(data);
      else if (event === 'status') handlers.onStatus?.(data);
      else if (event === 'final') finalPayload = data;
      else if (event === 'error') throw new Error(data.message);
    }
  }
  return finalPayload!;
}

7 RAG 系统深度剖析

RAG（Retrieval-Augmented Generation）是这个项目的核心能力之一。本章将深入剖析它的完整实现。

7.1 双层 RAG 架构

这个项目实现了两层 RAG，形成优雅降级链：

唯一可用的搜索 降级/增强 第 2 层 · LangChainRAGService 向量检索（ChromaDB + OpenAI Embedding） • 混合检索：向量 + 词法 + RRF 融合 • Small-to-Big：子块匹配，父块上下文 • 在线指标：多样性、置信度、覆盖率 • 自动构建向量库（如果为空）

7.2 Small-to-Big 分块策略

核心问题 如果把文档切成大块，检索精度差（不相关的内容也被检索到）；如果切成小块，上下文不够（LLM 只看碎片看不懂完整意思）。Small-to-Big 策略同时解决了这两个问题。

Small-to-Big 的工作原理：

  1. 创建父子块：每个文档切片创建两种块——小 子块（用于向量匹配，如 200 字）和大 父块（包含完整上下文，如 800 字）
  2. 只嵌入子块：只有子块被转成向量存入 ChromaDB（节省 Embedding 成本）
  3. 检索子块：用户查询时，向量检索找到最匹配的子块
  4. 返回父块：通过 _fetch_parent_context(parent_id) 把对应的父块（完整上下文）返回给 LLM

效果：检索精度高（小块匹配准）+ 生成质量好（大块上下文足）。

7.3 混合检索 + RRF 融合

单靠向量检索有盲区——对精确关键词不敏感。单靠词法检索也有盲区——对同义词和语义理解无能。混合检索取二者之长：

  • 向量检索：问题 → Embedding → ChromaDB 余弦相似度 → Top-K 结果
  • 词法检索：问题 → 关键词提取 → 类目匹配 → 词法重叠评分 → Top-K 结果
  • RRF 融合（Reciprocal Rank Fusion）：把两个排序列表合并成一个，公式为 score(d) = Σ 1/(k + rank_i(d))，k=60
RRF 的优势 不依赖具体分数的量纲（向量的余弦距离和词法的重叠分数不可直接比较），只关心「排名」本身。是一种简单但非常有效的融合方法。

在基础 RAG 之上，项目实现了一个可插拔的模块化 RAG 管道，9 个模块可以按需组合：

7.7 CRAG 与 Self-RAG

🔧 CRAG（纠正性 RAG）

评估检索结果的平均质量分。如果低于 0.3（质量阈值），提取核心查询词重新检索；如果低于 0.1（危险阈值），标记结果为"不可靠"。最多重试 2 次。

🪞 Self-RAG（自反思 RAG）

生成答案后，用 ReflectionEngine 在 3 个维度上评估：忠实度（答案是否符合原文）、相关性（答案是否切题）、完整性（是否覆盖所有要点）。不通过则重新生成 1 次。

8 文档处理流水线

8.1 完整流水线：6 个阶段

①

解析（Parse）

DocumentParser 门面按文件扩展名路由到 4 个解析器：PDFParser（PyMuPDF，含字体大小标题检测）、WordParser（python-docx，含样式段落）、ExcelParser（openpyxl，转自然语言行）、OCRParser（PaddleOCR，中英文图片识别）。统一输出为 DocumentSection 列表。

②

清洗（Clean）

DataCleaner 执行 4 步清洗：去噪（移除页眉/页脚/水印/版权行，10 种正则模式）、去重（MD5 哈希，相似度 > 0.95 的块合并）、质量评分（完整性 ×0.3 + 可读性 ×0.3 + 信息密度 ×0.4）、冲突检测（识别「可以/不可以」等矛盾陈述）。

③

分块（Chunk）

ChunkingEngine 支持 4 种分块策略：heading（按 Markdown 标题切分，默认）、recursive（递归字符分割 \n\n → \n → 。 → ； → 空格）、fixed（固定大小 500 字 + 50 字重叠）、small_to_big（父子块，用于 RAG 检索）。

④

血缘追踪（Lineage）

LineageTracker 记录每个块的完整处理历史：源文件、页面、章节、每一步的处理参数和时间戳。通过 trace_back() 可以回溯到任意处理阶段的原始数据。

⑤

版本管理（Version）

VersionManager 实现类似 Git 的知识库版本控制：create_version() 创建快照（JSON 文件）、diff() 比较两个版本的差异、rollback() 回滚到历史版本（回滚本身也创建新版本，保留完整历史）。

⑥

审计日志（Audit）

AuditLogger 记录所有文档操作：谁在什么时间对哪个文档做了什么操作，结果如何。支持按类目（document/query/system/sensitive）、操作、行为者、时间范围查询。自动清理超过保留期限的记录。

8.2 文档解析器门面模式

app/document/parser.py — 按扩展名路由python
class DocumentParser:
    def __init__(self):
        self._parsers = {
            '.pdf': PDFParser(),
            '.docx': WordParser(), '.doc': WordParser(),
            '.xlsx': ExcelParser(), '.xls': ExcelParser(),
            '.png': OCRParser(), '.jpg': OCRParser(),
            '.jpeg': OCRParser(), '.bmp': OCRParser(),
        }

    def parse(self, file_path):
        ext = Path(file_path).suffix.lower()
        parser = self._parsers.get(ext)
        if parser is None:
            raise ValueError(f"Unsupported file type: {ext}")
        return parser.parse(file_path)

这种「门面+策略」的设计让它非常容易扩展——要支持新的文件格式，只需写一个继承 BaseParser 的新类，然后注册一行。

10.3 常见追问及回答模板

❓ 「为什么不用 LangChain 的 Agent？」

「LangChain Agent 是黑盒，我需要精确控制工具调用流程——参数验证、错误处理、降级策略。自己实现 ReAct 循环给了我完全的控制力。但我在 RAG 层用了 LangChain 的 Embedding 和文本分割器，合理利用生态。」

❓ 「5 种 Agent 模式怎么选择的？」

「有两级决策：规则路由（正则+关键词，覆盖 80% 场景，零延迟）和 LLM 路由（分类提示词，处理模糊意图）。规则置信度 ≥ 0.8 直接采用，不够才走 LLM。既快又准。」

❓ 「RAG 准确性怎么保证？」

「多层保障：① 混合检索减少遗漏；② RRF 融合减少偏置；③ CrossEncoder 重排序提升精度；④ CRAG 检测低质量检索并重新检索；⑤ Self-RAG 反思答案质量并重新生成；⑥ 在线指标（多样性/置信度/覆盖率）实时监控。」

❓ 「如果部署到生产环境，还需要做什么？」

「① 把 SQLite 换成 MySQL/PostgreSQL；② ChromaDB 换成 Milvus/Pinecone；③ Redis 集群化；④ 加 API 网关和 WAF；⑤ 加监控告警（Prometheus + Grafana）；⑥ 加 A/B 测试框架；⑦ CI/CD 管道完善化。」

❓ 「这个项目最大的技术挑战是什么？」

「在 LLM 的'自由'和企业的'管制'之间找平衡。LLM 天然不可预测，但企业要求稳定、安全、可解释。我的方案是：安全护栏阻断危险输入、工具注册表限制能力边界、只读 SQL 防止数据污染、全量审计确保可追溯。」

❓ 「为什么用 Olist 数据集？」

「这是一个真实的巴西电商数据集，含 10 万+订单、用户评价、产品信息。用它可以让项目展示真实的数据分析能力，而不是虚构的玩具数据。面试官能看到我处理真实数据复杂性的能力。」

📖 术语速查表

术语全称一句话解释
LLMLarge Language Model（大语言模型）能理解和生成文本的 AI 模型，如 GPT-4
RAGRetrieval-Augmented Generation（检索增强生成）先检索知识再让 LLM 生成，减少幻觉
AgentAI Agent（智能体）能使用工具、能自主决策的 LLM 应用
ReActReasoning + Acting（推理+行动）LLM 先思考需要什么信息，再调用工具获取，再根据结果生成答案
Function Calling函数调用OpenAI 的机制，让 LLM 能「调用」你定义的函数
Embedding向量嵌入把文本转换成一串数字（向量），语义相似的文本向量也相近
ChromaDBChroma 向量数据库本地向量数据库，存储和检索文档向量
RRFReciprocal Rank Fusion（倒数排名融合）把多个搜索结果列表合并成一个的算法
CRAGCorrective RAG（纠正性 RAG）评估检索质量，必要时重新检索
Self-RAGSelf-Reflective RAG（自反思 RAG）让 LLM 反思自己的答案质量并改进
LangChainLangChain 框架封装 LLM 开发常用操作的 Python 框架
LangGraphLangGraph 状态图引擎用节点+边定义 Agent 工作流，支持条件和循环
MCPModel Context ProtocolAnthropic 提出的 AI 工具调用标准协议
SSEServer-Sent Events（服务器推送事件）服务器主动向浏览器推送数据的技术
JWTJSON Web Token无状态的认证令牌，服务器靠签名验证
RBACRole-Based Access Control（基于角色的访问控制）按角色分配权限，不是按用户个体
FastAPIFastAPI 框架Python 异步 Web 框架，自动生成 API 文档
PiniaPinia 状态管理Vue 3 的状态管理库，替代 Vuex
PydanticPydantic 数据验证用 Python 类型注解做运行时数据验证
CrossEncoder交叉编码器对查询和文档同时编码，判断相关性（比向量检索更准但更慢）
BFSBreadth-First Search（广度优先搜索）一种图遍历算法，用于知识图谱的多跳检索
OlistOlist 电商数据集巴西电商平台的公开数据集，含订单/评价/产品
